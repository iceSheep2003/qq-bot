# 当前架构与多群记忆边界

更新时间：2026-10-16

本文件说明运行时一致性和记忆范围。目录与依赖以 [架构说明](README.md) 为准。
群聊和可选私聊分别经过场景准入；下文的群级隔离规则同样要求私聊保持独立 scope。
不同群和私聊的记录保持隔离。`PersonalContinuity` 为同一用户的私聊提供少量公开自述偏好，
它不读取全量 Wiki、不传播私聊，也不改变任何工具范围；内部策略只由系统和部署者管理。

## 1. 扩展边界

内核工具、权限、数据库迁移和本体 schema 都由版本代码维护。部署者以
`SKILL.md` 补充表达指导，以声明式任务定义选择既有动作的排期；Skill 不能安装程序、注册工具、写
数据库、修改权限或通过聊天热更新。需要真实新能力时，修改受审查的内置代码。

模型只能看到固定的内置工具：对话读取、知识检索与证据、群查询、媒体目录、视觉、
音频转写、原生互动、群管理提案和 Skill 加载。每个工具都在代码中做参数、作用域、
配额和执行状态校验。

## 2. 一个 QQ 用户跨多个群时怎么处理

默认策略是“身份可相同，记忆不串群”。同一个 `user_id=7` 在 `group:42` 和
`group:43` 会产生两个独立的主体键：

```text
person(group:42, 7) != person(group:43, 7)
```

以下数据仍只在产生它的群内可读：

- 消息账本、短期窗口、压缩快照和 Prompt Session；
- 个人经历、偏好、情绪、好感度、称呼、名片和关系阶段；
- 该人的语言风格样本、群内黑话、话题、承诺、行为图谱证据；
- 媒体资产、引用消息和群管理提案。

因此，A 群里的聊天不会被拿到 B 群续聊，A 群的好感度也不会改变 B 群的称呼。
私聊可以通过公开偏好认出同一个人：只有源消息确由本人在白名单群中发出，且记忆标记为
`preference`、`group` 可见、`active`、可信度至少 0.8、未过期、允许直接或轻度提及时才可读取。
每次最多三条，整个贡献不超过 1000 字符。黑话、关系、边界、私聊资料与他人信息均不在此路径。
这一路径直接查询当前来源状态，不生成第二份可长期残留的全局副本；删除或归档原记忆后不再读取。
聊天用户不能通过指令设置或撤销内部记忆策略，聊天链路不提供相应管理命令。
任何相关文字都按普通消息处理，同样经过每日私聊人数准入；不产生配置回执。
部署者的本地管理操作可以限制背景读取，已经发送过的真实对话不会因此被重写。

允许共享的只有部署者明确提供的、与个人无关的只读内容：基础人格规则、脱敏后的
公共表达模式、已经确认的公共词义，以及不包含群成员身份的行为经验。当前行为经验
文件不以真实 QQ 人物为节点，因此可以被多个群只读使用；群内的动态经验仍按 scope
保存。

## 3. 在线回合

1. OneBot 入站先做白名单和去重，再写入实际消息账本；未授权群不会进入记忆或图谱。
2. 同一群进入有界 FIFO lane，严格串行；不同群可以并行，模型客户端有全局并发上限。
3. Agent 读取当前群的动态窗口、引用、Bot 已成功发送的最近内容和本群长期记忆。
4. `MemoryContextPolicy` 只把有证据的、当前 scope 且主体匹配的记录放入本轮；主动群聊
   只读取群级话题/黑话，不读取个人隐私。
5. Planner 返回文字、表情、语音、引用和原生互动的候选计划；Executor 校验目标后发送。
6. 只有平台回执为成功的部分才写入“我说过”的账本和 Prompt Session。发送失败或未知
   不会被模型误认为已经说过。
7. 实际入站消息写入后，由 `ConversationMaintenance.maybe_extract` 按消息数间隔调度长期记忆
   提炼，同一 scope 同时最多一个提炼任务，所有 scope 默认共享两个提炼槽位；无需触发回复。
8. 回复成功发送且记账后，由 `ConversationMaintenance.after_reply` 调度短期压缩，
   `ObservationDispatcher` 调度情绪、好感度和行为观察。压缩跳过 operator 来源，自动好感度
   仍只用于群聊；这些维护任务不阻塞下一轮回复。

## 4. 短期窗口与长期记忆

短期窗口由消息数、时间和字符数共同限制。热聊达到阈值时，后台压缩器只处理旧段，
保留最近尾部，并用 CAS 提交连续性快照；失败时保留原始账本。快照明确区分群友和 Bot，
记录 Bot 实际说过的话、承诺和未闭环话题。

长期记忆分为事实、主题和行为经验。事实必须带来源事件和可验证证据，撤回/过期/冲突
记录不会继续出现在在线上下文。长期记忆是背景资料，不是当前指令，也不进入稳定前缀。

Wiki 批量发布以 `.wiki-managed-pages.json` 记录程序生成的页面。下一次发布会清理不再存在的
生成页，包括空快照；未登记的手写 Markdown 不会被清理。读取器检测文件集合变化后同时清空
TTL 上下文缓存。发布先校验清单路径，全部页面写入成功后才清理旧页；单页写入失败不会
替换所有权清单或删除先前的页面。清单从首次生成时开始建立，升级前没有登记的文件保留，
由部署者核对来源后处理；不要把手写内容放进已由程序管理的生成页中。

Wiki 的批量阈值计算“相对上次发布，实际改变了多少条已发布事实、主题和黑话”，不计算
数据库总行数。逐条指纹随同步状态持久化，重启不丢基线；访问次数、最近读取时间、来源行
顺序和未发布候选不触发版本变化。普通变化累计到八条或十分钟后发布；已发布内容被删除或
变成不可发布状态时，在下一次来源检查中优先替换，不等累计窗口。来源检查仍默认每六十秒一次。

## 5. 并发与公平

- 每群一个入站 lane，队列有界；热群不能无限堆积内存。
- 所有模型请求共享 `BOT_MODEL_MAX_CONCURRENCY` 槽位，记忆提炼、压缩、情绪、人格和
  对话都受同一上限保护。
- 每个会话的回合由 scope lock 串行；后台压缩每个 scope 同时最多一个任务，默认每分钟
  最多接受两次，采用“回复后维护”。群聊和私聊各自计算预算与占用。
- 提炼与压缩的任务表只由 `ConversationMaintenance` 持有。退出时拒绝新维护任务，取消并
  等待运行中和等待提炼槽位的任务；即使观察队列的关闭失败或被取消，也等待维护清理完成。
  历史账本、提炼算法和压缩器的 CAS 提交规则保持原样。
- SQLite 当前是单进程存储；多进程部署必须先启用单实例或增加租约/队列，不可直接启动
  两个 bot 进程，否则可能重复发送。

## 6. 后续实现顺序

1. 为每个群补充队列长度、模型等待、token、缓存命中和失败指标。
2. 给后台任务增加按群的令牌桶/公平轮转，避免一个热群占满维护槽位。
3. 增加跨群回放测试：同一 QQ 号在两个群的事实、关系、黑话、风格和压缩快照必须互不可见。
4. 在真实 NapCat 联调前验证白名单、断线重连、成功回执记账和重启去重。
