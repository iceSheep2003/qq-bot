# Kinna bot 上线验证与回滚

本指南供部署者使用。当前代码已完成本地验证；实际 QQ 平台和服务商联调需要使用明确的测试
账号与白名单群，部署属于独立操作。不要把本地测试通过当成已上线。

## 准备独立验证目录

记录现有实例的 Git 提交、工作目录、启动命令和环境文件位置。旧实例可能仍使用 `qunbot`，
新版本使用 `qqbot` 或 `kinna-bot`；切换和回滚都必须使用对应版本的真实启动入口。

备份环境、人格、任务配置、SQLite 数据、Wiki 和本地素材。SQLite 使用 backup API 或停止
实例后的完整副本，不能只在运行时随意复制主文件而漏掉 WAL。备份含密钥和聊天信息，留在
部署者自己的受限目录。不要用 `.env.example` 或空数据库覆盖线上状态。

在独立源码目录和虚拟环境中安装当前分支，用数据库副本和配置副本执行本地检查。
`qqbot --check` 会打开并迁移指定数据库，所以必须先明确 `BOT_DB_PATH`。

```bash
npm ci --prefix .code-quality-gate/toolchain --ignore-scripts
node .code-quality-gate/toolchain/node_modules/code-quality-gate/src/cli.mjs gate
qqbot --check
```

以上命令要求已按开发约定安装锁定的 Python 工具链并加载副本环境。程序不自动加载 `.env`。
`--check` 不调用真实 QQ 或模型服务，不能证明远程鉴权和模型名有效。仅私聊部署可不设群
白名单，也不需要不存在的群任务文件。私聊每日人数默认十人，按配置时区计算，重启保留计数。

## 真实平台联调顺序

先停止会争抢同一个 QQ 接入或数据库的旧实例，再让测试实例连接指定 NapCat。先只开
测试群的文字回复，保持图谱、定时发言和其他外部能力关闭，再逐项确认：

1. 白名单消息能入账，非白名单群不入账；群聊和私聊分别遵守准入配置。
2. 一次正常提问只收到一次回复；引用目标和媒体素材属于本场景。
3. 重启和断线重连后不会重发已确认的消息；失败或未知的发送不会被记成已发送。
4. 私聊人数设为较小值后，超额新用户不触发模型、媒体理解或长期记忆提炼，已有名额者仍能继续。
5. 人物连续性自然使用本人公开偏好；不泄露私聊、他人资料和其他群的人物关系，不出现设置回执。
6. 观察回复延迟、错误日志、请求用量和真实缓存命中。缓存未知不能按零或命中处理。

测试会产生真实消息与模型费用。先完成文字路径，再按需要验证语音、表情、群任务等能力。
图谱数据清洗与重建另立实验；私聊定时任务不在本轮产品范围内。

## 切换与回滚

正式切换前记录通过验证的提交和配置，确认旧实例已退出；只启动一个写同一数据库的进程。
保留升级前快照和旧启动命令。启动失败、持续重复发送、场景串线或费用异常时先停止新实例，
保存当前数据与日志副本，然后按已记录的旧源码、环境和数据库快照恢复。

不要直接删除新版本运行后的数据来回退。先保留它，新增对话需要单独核对或迁移。恢复旧版本
后先验证连接与一条测试消息，再恢复原有群和任务范围。未完成这些现场步骤时，只能记录为
“本地验证通过，等待上线联调”。
