# QunBot 模块现状与接手开发路线

本文供后续开发 agent 使用，基于当前源码而非目标愿景。项目仍是原型：现有测试与本地配置检查通过，不等于每项能力都完成了 NapCat、模型服务和真实 QQ 群联调。更改运行代码后，已启动的旧进程不会自动加载新版本。

## 一、先遵守的边界

群聊话题识别、相关消息选择与 append-only Prompt Session 的目标架构见
[`CONVERSATION_INTELLIGENCE_DESIGN.md`](CONVERSATION_INTELLIGENCE_DESIGN.md)。实现时以该文档定义的本地算法、领域端口和分阶段验收为准，不要重新把这些职责塞回 `runtime.Agent`。

- 这是部署者拥有的对话 Bot。群成员只能聊天，不能借聊天命令安装扩展、改人格、改好感度、创建任务或读取数据库；不要引入这类管理工具。
- 核心能力：NapCat 接入、入站过滤与会话、回复决策、Agent、稳定人格、长期记忆、按群友划分的关系与好感度。定时引擎是基础设施，不认识任何具体海报或主动续聊内容。
- 可选运行时代码：海报、定时闲聊、随机续聊、情绪、表情包、语音，以及将来的黑话学习、动态人格、风格模仿、天气等。启用权只在本地配置 BOT_EXTENSIONS 和扩展允许名单。
- Skill 是提示说明，不是运行时插件。禁用能力时不应向模型展示其 Skill。扩展需要执行代码、访问数据库或发送消息时，必须提供受控的 Python 实现及端口，不能仅写 SKILL.md。
- 依赖方向：domain/ports ← runtime、memory、relationships、scheduling ← adapters/storage/extensions ← app 装配。核心模块不能导入 extensions、Pillow、NapCat 或具体模型客户端。
- 不要把来自群消息、记忆、网页或扩展的内容写入稳定人格文件。用户内容、临时人格、回忆和工具结果都属于低信任的本轮数据。
- 真实 .env 含私密配置，不提交、不复制到测试或文档。开发与测试默认不连 NapCat，不往群里发消息。

## 二、当前包和下一步

### domain.py、ports.py、config.py、app.py：契约与装配

已实现：MessageEvent 等基础对象和协议端口；本地环境配置；app 装配模型、仓储、Agent、扩展、NapCat 和定时引擎。扩展只从 loader 的本地允许名单导入。

缺口：协议仍有宽泛的 dict 和 Any；扩展的启动、校验、关闭分别走多套函数；配置是环境变量集合，缺少跨字段校验和明确的配置版本。app 的资源构建中途失败时尚无统一的逆序清理。政策对象 BotPolicy 还混有会话与定时任务的参数。

开发：先为消息、模型结果、任务请求/结果、上下文片段定义稳定的类型；按 ConversationPolicy、SchedulePolicy 拆分政策；将可选模块的配置解析与校验放在其包内。为装配增加失败时的清理和运行时生命周期测试。不要为可选功能向 Config 追加海报日期、语音参数等业务字段。

验收：禁用某扩展时，其模块和重依赖不被导入；未知扩展、重复 action 或缺失配置启动即失败；app 装配失败不遗留数据库连接或 HTTP 客户端。

### adapters/events.py、onebot.py：NapCat/OneBot

已实现：反向 WebSocket、Bearer Token、群/私聊消息解析、@ 识别、图片 URL 提取、文本/图片/语音发送；按连接保存请求 echo 并等待响应。群白名单和私聊开关在服务层。

缺口：每个入站帧直接创建后台 task，没有有界队列、按群顺序或背压；重复与重连仅靠消息表唯一键处理。图片只把 URL 传给模型，未验证链接有效期与可达性。发送失败、断线和超时缺少统一重试/不重试策略；@ 发送能力存在，但对话输出没有明确的“向谁 @”结构化决策。

开发：定义入站事件队列和每群串行执行器，限制并发与积压；为 OneBot 原始事件、响应、断线和图片/语音消息写录制回放测试。把 @ 目标放在受验证的回复结构里，由发送层校验只引用当前群成员，不能让模型拼任意 OneBot 指令。先用模拟 gateway 测试，真实 QQ 测试另行显式进行。

验收：重连、重复消息、乱序、响应超时、恶意/畸形帧都不会造成重复回复或无限创建 task；非白名单群和禁用的私聊不写入会话。

### adapters/model.py：模型提供商

已实现：OpenAI 兼容 chat/completions 请求、工具 schema 透传、模型 usage 返回；Agent 记录稳定前缀摘要。当前本地配置使用 Grok 兼容入口。

缺口：尚未验证该服务商真实的 prompt cache 命中和多模态/工具调用行为；没有区分超时、限流、临时错误和永久错误；缺少模型能力声明、故障退避和调用预算。不要从 SHA 摘要相同推断已命中服务商缓存。

开发：在适配器边界添加能力描述、重试与超时策略，保留原始 usage 中服务商返回的 cached_tokens 字段；用假服务端测试错误和工具调用协议。将密钥、输入/输出敏感内容从日志中排除。对缓存优化先做测量：固定同一前缀、多轮请求，记录 prompt_tokens、cached_tokens、前缀哈希和消息序列变化。

验收：同一稳定人格与启用 Skill 集合的前缀字节恒定；动态群消息/好感度/记忆/时间不进入该前缀；缓存指标缺失时标记“未知”，不当成 0。

### runtime/agent.py、context.py、skills.py、tools.py：对话编排

已实现：人格从 config/persona.md 读取；稳定 system 前缀包含人格和已启用 Skill 目录；最近 18 条会话、发言人好感度、相关记忆、按触发词选中的 Skill 与扩展上下文进入动态后缀；最多 4 轮模型工具调用。工具注册表当前内置只读记忆检索。

缺口：上下文贡献是任意值，没有大小、优先级、超时和敏感级别；长会话没有 token 预算和摘要；最近记录与图片可能耗尽上下文。Skill 用简单字符串触发和手写 frontmatter 解析，不等于成熟的技能发现。工具调用缺少输入 schema 执行时校验、异步/超时、权限与每轮预算，工具返回值只按字符截断。

开发：定义 ContextContribution（来源、scope、优先级、token 上限、TTL、信任级别），在动态后缀按预算裁剪；保持稳定前缀不变。将回复决策从生成文本中拆开：基础策略仍只有 @，高级 Group Chat Plus 式“读空气”实现可替换的 ReplyDecisionPolicy，允许明确 abstain。工具保持部署者注册和最小权限，默认不得暴露写好感度、改人格、创建任务或任意 HTTP/文件系统。

验收：极长消息、记忆和扩展上下文有可预期上界；未启用 Skill 不出现在模型目录；模型请求的未知/非法工具不可执行；不同群的动态上下文不会串用。

### runtime/service.py：会话生命周期

已实现：群白名单、私聊禁用、入站去重、后台记忆提炼触发、仅被 @ 回复、按 scope 锁串行回复、发送后记录消息和异步关系/情绪观察。定时分发已移出本类。

缺口：回复策略仍是硬编码的“群聊仅 @”；内存锁、last_reply 与正在提炼集合在重启后丢失；每个回复后的观察任务直接 create_task，没有队列、取消或等待完成机制。数据库调用是同步 SQLite 操作，可能阻塞事件循环。

开发：将 ingest、reply decision、turn execution、post-reply events 分为独立用例；异步观察采用有界队列和幂等事件 ID；为单群串行、跨群并行、正常关闭与失败重放写测试。不要让扩展直接改 ConversationService 私有字段。

验收：群消息只记录一次；失败/断线不会重复计好感度或记忆；停机时后台观察任务有清晰的完成或恢复规则。

### memory/service.py、storage/memory.py：长期记忆（LivingMemory 主参考）

已实现：每 N 条用户消息，模型从最近 20 条提炼最多 3 个事实；按 scope、user_id 存入 SQLite；FTS5 搜索，未命中时 LIKE 回退；本轮检索最多 4 条注入，另有只读 recall_memory 工具。尚不是完整 LivingMemory。

缺口：没有独立的采集候选、审核/置信度、事实冲突处理、来源/有效期、访问强化、归档/遗忘和敏感信息策略；没有向量与结构化关系检索。中文 FTS 与 LIKE 回退较粗；当前默认检索按 scope 而非严格按“群 + 被谈及的群友”，容易混淆发言人与事实主体。

开发顺序：

1. 明确 MemoryItem 的群、主体用户、事实类型、来源事件、置信度、重要性、创建/过期时间、可见范围和状态；设计 schema migration，不删现有记录。
2. 将消息采集、事实提炼、去重/冲突、检索、排序、动态注入分开；写入须幂等，低置信事实先成为候选。
3. 在现有词法检索上增加可选 embedding 提供者和混合排序；向量不可用时退回词法检索，不让 Bot 无法启动。
4. 增加生命周期（过期、归档、访问强化、明确遗忘）和个人/群级分区、隐私删除测试；图谱关系检索放在这些稳定后再做。

验收：能解释每条注入记忆来自哪里、为何入选；不同群与不同人的记忆不串用；删除一个用户信息后 FTS/向量索引也同步移除；稳定缓存前缀不受记忆更新影响。

### relationships/evaluator.py、storage/relationships.py：群友档案与好感度

已实现：全局昵称、按 group_id + user_id 独立的 -100..100 好感度、变化原因；每人每群一小时冷却；回复后模型判断是否有明确关系意义，普通寒暄和用户请求改分不生效。

缺口：模型评分质量和操纵抵抗未经真实群验证。已补齐：可配置关系阶段、审计查询（`history`/`explain`）、休眠衰减（`BOT_AFFECTION_DECAY_HALF_LIFE_SECONDS`，默认关闭）。仍未做：关系**类型**（本模块刻意只有一个 bot↔用户标量，没有插件那套父母子女/同事/队友的分类法）；用户隐私开关。昵称表目前按 user_id 全局存，群名片不是按群保存。没有把好感度与回复策略/措辞建立明确、可测试的影响规则，当前只是将数值放进动态上下文。

开发：将“群友事实档案”与“互动关系状态”分开建模；评分提议和正式写入分层；建立用户级与群级作用域和防刷分规则；用关系阶段而非裸数值给 Agent 提供有界叙述。借鉴 MoreMoreLove 的互动反馈，但这个模块是唯一关系数据所有者，Self Learning 不另建第二张好感度表。

验收：同一 QQ 在两个群关系互不影响；群消息不能直接命令改分；每次变化有来源事件和解释；未启用自动评分时档案仍可读。

### emotion/ 与 extensions/mood/：Bot 自身情绪

已实现：五维状态、衰减与自然语言描述；回复后独立模型评估；低社交意愿可阻止随机主动发言；可关闭模块或只关闭自动评估。状态存在独立 SQLite。

缺口：缺少异常/重复观察幂等、状态演化回放及长期校准；情绪与关系/人格的职责可能重叠。天气与时间感知、记忆回放尚未实现，不能把 Connectome 的全部能力算作本模块已交付。

开发：固定状态事件与衰减时钟的可重复测试；定义输入信号仅“Bot 自身状态”，不写群友好感度，也不改稳定人格。若新增时间/天气/回放，作为独立 world_context 扩展向动态上下文贡献，外部天气接口可禁用/降级。

验收：相同事件重复投递不重复改变心情；重启后状态可恢复；扩展关闭时不创建情绪数据库，不影响群聊。

### scheduling/、storage/jobs.py：通用定时基础设施

已实现：at、every、五段 cron，任务建议默认禁用；本地 schedules.json 接管并启用；持久化下次执行/执行结果，错过任务不补发；JobRunner 统一检查群白名单与活跃时段，具体 action 在本地注册。

缺口：没有完整的时区/DST 测试、按任务误触发策略、租约/多实例互斥、执行超时和独立的重试策略；任务参数当前主要是 prompt 字符串，难以扩展类型化 payload。重启前后的去重语义需要明确（尤其发送成功但结果未落库）。

开发：版本化 JobSpec/JobRunResult、各 action 自己的参数校验；定义 misfire、超时、幂等键和单实例假设。若将来多进程运行，先加入可过期租约，再考虑重试。cron 触发不等于“Bot 必须发言”：handler 可以有明确的 skipped 结果。

验收：过期一次性任务不补发；重复调度不会同一 run_id 发两次；任务未注册/扩展停用时启动检查报错，不在群里输出异常。

### extensions/scheduled_chat/、proactive_chat/：计划与主动水群

已实现：scheduled_chat 是注册的 chat action，有每日配额、冷却、群活跃、去重/字数检查；proactive_chat 是可选的 60 秒轮询 worker，有限额、活跃时段、近期对话和随机门控。当前本地配置启用了前者，未启用后者。

缺口：随机续聊不是 AIReplay 式持久化“最后一条消息之后 X 分钟”工作流；免打扰只有通用活跃时间段，没有群/人的细粒度策略；随机概率和部分时长写在代码里；last_reply 重启后丢失。

开发：复用 scheduler 的 at/every/cron 和本地 JobSpec，把定时续聊、消息后间隔续聊作为不同触发条件/任务策略；增加每群免打扰、冷却、上下文新鲜度、当次沉默决策。不要另建一套与 scheduler 平行的 cron 引擎，也不要让群成员创建提醒任务。

验收：启用/禁用扩展和任务互不影响普通 @ 回复；Bot 不会在同群短时间重复发言；时段外与群冷清时日志为 skipped。

### extensions/exam_poster/：海报只是 JobAction

已实现：仅注册 poster action 时导入 Pillow 和海报渲染器；日期/字体由本包读取；本地绘图，模型配文失败可回退。它不是 Bot 核心能力。

缺口：海报模板固定为考研倒计时；没有通用海报协议、布局模板、字体资源包或渲染结果快照测试；图片实际在 NapCat 发出的表现尚需验证。

开发：保留 exam_poster 独立包；若以后增加生日/周报海报，创建独立 action/renderer 或抽象通用 Renderer 端口，但不要在 scheduler、ConversationService、Config 里写新的业务分支。绘图测试不依赖外部模型。

验收：不安装 Pillow 且不启用 exam_poster 时纯聊天 Bot 正常启动；启用但缺日期/字体时启动检查明确报错；考试结束标记 skipped。

### extensions/memes/、voice/、media.py：媒体

已实现：本地表情 catalog、文件路径限制与体积上限；voice 可选 OpenAI 兼容或 DashScope 语音源；模型回复中的私有标记驱动媒体发送。当前本地配置启用 memes，voice 未启用。

缺口：没有表情语义检索、群内素材学习/审核、媒体复用与压缩；图片/语音 OneBot 端到端兼容性尚未验证；语音音频 URL、时长、格式、失败回退需实测。直接从不可信群消息学习图片不可默认开启。

开发：先把出站消息建模为 Text/Image/Voice/At 结构，替换混在自然语言中的标记；添加素材来源、版权/同意、管理员本地审核和限额。图片入站由单独视觉适配器下载与转交模型；必须验证 URL、文件大小、MIME 和超时。语音仍是可选扩展，不得成为启动必需项。

验收：禁用 voice 不创建其 HTTP 客户端；TTS 故障回退文本；超大/无效媒体不会使整个会话失败；@ 目标由结构化消息校验。

### extensions/loader.py、features.py 与 skills/：扩展机制

已实现：本地显式允许名单，分别注册 JobAction、后台 worker、动态上下文、回复后 observer、工具、媒体和清理回调；启用的 Skill 才加入稳定目录。没有群聊热安装入口。

缺口：JOB/BACKGROUND/FEATURE 仍是三个映射；未定义版本化扩展 manifest、依赖/冲突、注册阶段和统一卸载生命周期。context provider 无预算与故障隔离；扩展工具尚无权限声明、调用配额和审计。Skill 触发器只是简单子串匹配。

开发：定义本地声明式 manifest（名称、版本、最低契约版本、依赖、贡献类型），将启动校验/注册/关闭统一起来；保持“部署者修改代码或配置后重启”模式，暂不做群聊管理或任意第三方热加载。限制每个扩展的上下文大小、工具权限、后台并发和失败传播。先写契约测试再增加新扩展。

验收：重复注册与依赖缺失会在启动前报错；某个可选上下文提供者失败不会打断普通 @ 回复；未经允许的代码即使放在 extensions/ 目录也不会运行。

### 尚未创建的拟人功能包

- Dynamic Persona：可选 per-turn persona_strategy，输出临时性格增量并限定 TTL；绝不覆盖 config/persona.md。先确定与 mood 的优先级。
- Echo Avatar：仅对部署者指定且适当取得同意的用户采集表达样本，风格资料与 Bot 稳定人格分离；避免未经允许冒充具体群友。
- Self Learning：群内黑话候选 → 频次/上下文证据 → **模型分阶段推断含义（差分法：脱离上下文也能定义的就不是黑话）** → 人工或本地规则审查 → 按当前消息命中的受限上下文贡献；好感度由 relationships 写，记忆由 memory 写，学习包不得复制所有权。
- Group Chat Plus：独立回复决策策略，输入群上下文与 @ 状态，输出 reply/abstain + 理由；先离线回放评估误回复率，默认仍只 @。
- Connectome：world_context 和内部状态策略的参考；时间/天气/记忆回放拆成可分别禁用的提供者，不混入稳定前缀。
- Private/Memory Companion：角色状态可作为扩展，记忆分区仍由核心 memory 统一维护。它们不是 LivingMemory 同团队，勿按作者关系推断实现一致。

这些是参考方向，不代表现有包已交付，也不意味着直接复制 AstrBot 插件源码。若移植开源实现，先核实各仓库许可、版本、依赖和实际代码；优先移植行为与测试，而不是把 AstrBot 的事件类型引入核心。

## 三、建议的工作顺序与并行边界

1. **P0 安全和可观察性**：补 Agent token/context 预算、消息队列/并发上界、异常与关闭处理、模型缓存指标、隐私删除/来源测试。为后续功能建立可信基线。
2. **P1 记忆与关系**：先定数据模型和迁移，再做采集/检索/注入；并行可开发关系状态策略，但不要同时修改 ports.py、app.py 和同一份 schema。
3. **P2 回复决策、拟人状态与学习**：分别在独立包实现，先使用离线群消息回放，不直接打开主动群聊。公共贡献契约变动由一名集成 agent 统一合并。
4. **P3 主动互动/媒体联调**：把 AIReplay 式续聊落在调度机制上；海报、语音、读图逐项单独验收，先模拟 OneBot，再经部署者明确选择在测试群验证。

可并行的子任务是：记忆检索算法（只改 memory/storage/memory）、回复决策策略（新包与离线测试）、媒体适配（只改对应 extensions 子包）、文档/契约测试。需要串行集成的共享文件是 ports.py、app.py、config.py、extensions/loader.py、storage/database.py 和 schedules.json。各 agent 不应同时编辑这些文件；先约定接口，再交给集成 agent 接线。

## 四、交付检查单

- 说明本次修改属于核心、基础设施还是哪一个可选扩展；列出新/变更的端口与数据表迁移。
- 给纯单元测试、故障/禁用测试、真实平台测试分别标记结果；不要把模拟 gateway 测试写成“已在 QQ 验证”。
- 运行：.venv/bin/python -m unittest discover -s tests -q；.venv/bin/python -m compileall -q qunbot；git diff --check。
- 带本地环境变量运行 qunbot --check；它会同步任务配置到本地数据库，但不连接 NapCat。不要在测试里读取或打印真实 .env 密钥。
- 给缓存相关改动记录稳定前缀摘要、动态段位置及服务商实际返回的 cached_tokens；没有这个字段不能声称缓存命中改善。
- 禁用可选扩展的启动检查必须通过；普通群聊不能因为海报/语音/天气服务未安装而失败。
- 不主动重启现有进程、发送 QQ 测试消息或修改群任务配置，除非该开发任务明确授权；先把变更和所需联调步骤交给部署者。
